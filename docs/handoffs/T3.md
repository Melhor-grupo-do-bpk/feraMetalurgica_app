## Pedidos

### HO-T3-01: orçamento com custos zerados pode ser concluído?
- **Tipo:** dúvida (para a lista de perguntas ao cliente da T8)
- **Arquivo(s):** `lib/features/orcamentos/presentation/wizard/orcamento_wizard_controller.dart`
- **O quê:** a etapa 3 aceita avançar com total R$ 0,00, e o orçamento é
  gravado com valor final R$ 0,00.
- **Por quê:** nenhum requisito (RF-23) pede um mínimo, e o responsável
  decidiu não bloquear. Falta confirmar com o cliente se faz sentido
  exigir total maior que zero (ou pelo menos um aviso).
- **Trecho proposto:** se o cliente pedir o bloqueio, uma linha em
  `etapaValida`:
  ```dart
  3 => calcularTotalCustos(orcamento.custosOperacionais) > 0,
  ```
  e um `SnackBar` na página, como o da etapa 2.
- **Enquanto isso:** a etapa 3 sempre é válida. O comentário de
  `etapaValida` cita este handoff.

### HO-T3-02: `StepProgressBar` não aparece (segmentos com altura 0)
- **Tipo:** mudança em compartilhado (bug da F1)
- **Arquivo(s):** `lib/core/widgets/step_progress_bar.dart`,
  `test/widget/core/step_progress_bar_test.dart`
- **O quê:** os segmentos são `DecoratedBox` sem filho dentro de uma `Row`
  com `crossAxisAlignment` padrão (`center`). A `Row` passa restrição de
  altura frouxa (0 a 8), então cada segmento fica com altura 0 e a barra
  não é desenhada. Medido no teste: `Size(186.0, 0.0)`. O teste atual só
  confere a cor pela `ValueKey`, por isso não pegou.
- **Por quê:** RF-20 pede a barra de progresso no wizard (Telas 2 a 5).
  Hoje o wizard mostra só um espaço vazio no lugar dela. Não há como
  contornar dentro da T3 sem duplicar o widget (regra 1 do `CLAUDE.md`).
- **Trecho proposto:**
  ```dart
  child: SizedBox(
    height: 8,
    child: Row(
      crossAxisAlignment: CrossAxisAlignment.stretch,
      children: [
  ```
  e, no teste do widget:
  ```dart
  expect(
    tester.getSize(find.byKey(const ValueKey('step-segment-0'))).height,
    8,
  );
  ```
- **Enquanto isso:** o wizard usa `StepProgressBar(etapaAtual: etapa)`
  normalmente; a barra passa a aparecer assim que a correção entrar, sem
  mudança na T3.

### HO-T3-03: botões do `ItemCard` com área de toque menor que 48 dp
- **Tipo:** mudança em compartilhado (sugestão para a T8, não bloqueia)
- **Arquivo(s):** `lib/core/widgets/item_card.dart`
- **O quê:** "Editar" e "Excluir" usam `IconButton` com
  `visualDensity: VisualDensity.compact` e ícone 16, abaixo dos 48 dp de
  RNF-06.
- **Por quê:** acessibilidade (RNF-06). O wizard (etapa 2) é a tela que usa
  esses botões.
- **Trecho proposto:** remover o `visualDensity: VisualDensity.compact`
  (o `IconButton` volta ao mínimo de 48 dp), ou manter o visual compacto
  com `style: IconButton.styleFrom(minimumSize: const Size(48, 48))`.
  Conferir o espaçamento do card contra a Tela 3.
- **Enquanto isso:** o wizard usa o `ItemCard` como está.

### HO-T3-04: seeds #00482 e #00481 têm CPF/CNPJ inválidos
- **Tipo:** mudança em compartilhado (dados de exemplo)
- **Arquivo(s):** `lib/features/orcamentos/data/orcamentos_seed.dart`
- **O quê:** `123.456.789-00` (#00482, João da Silva) e
  `12.345.678/0001-90` (#00481, Metalúrgica ABC) não passam em
  `validarCpfCnpj`. Ao editar esses orçamentos, a etapa 1 mostra "CPF
  inválido"/"CNPJ inválido" e só avança depois de corrigir o documento.
- **Por quê:** o wizard aplica a validação de RF-21 também na edição, o que
  está certo, mas os orçamentos de exemplo mais visíveis (o #00482 é o do
  Figma) parecem quebrados para quem testa o app.
- **Trecho proposto:** trocar pelos documentos válidos mais próximos
  (conferidos com `validarCpfCnpj`):
  ```dart
  cpfCnpj: '123.456.789-09',      // #00482
  cpfCnpj: '12.345.678/0001-95',  // #00481
  ```
  Nenhum teste lê esses documentos do seed: os outros usos de
  `123.456.789-00` (`orcamento_json_test`, `validators_test` e os testes da
  T3) são literais próprios, e devem continuar como estão. O Figma usa
  `123.456.789-00` como placeholder, e o wizard o mantém só como
  `hintText`, que não precisa ser válido.
- **Enquanto isso:** os testes de edição da T3 usam o #00478 (CPF válido).
